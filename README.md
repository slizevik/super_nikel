## Часть 1. Описание проекта

### 1.1. Что это

**Nikelpower** — сервис для учёных-материаловедов, позволяющий искать информацию в общей базе исследований, докладов, статей и презентаций через диалог с LLM. Учёные загружают документы (PDF), система извлекает из них знания, строит единый глобальный граф связей и делает их доступными для семантического и структурированного поиска.

### 1.2. Зачем это нужно

Материаловедение — область, где знания распределены по тысячам публикаций. Исследователю сложно:

- найти все эксперименты по конкретному материалу и процессу;
- сравнить отечественную и зарубежную практику;
- увидеть противоречия между источниками;
- понять, где есть пробелы в данных.

Сервис решает эти задачи за счёт:

- единой базы документов с метаданными;
- глобального графа знаний, отражающего связи «материал → процесс → оборудование → результат» (сущности из разных статей объединяются в одни узлы);
- диалогового интерфейса, который подбирает релевантные источники и формирует ответ со ссылками на оригиналы.

### 1.3. Пользовательские сценарии

1. **Загрузка документа.** Учёный загружает PDF. Система обрабатывает документ, добавляет его в базу. Прогресс виден пошагово. Оригинальный PDF гарантированно сохраняется.
2. **Поиск через чат.** Учёный задаёт вопрос на естественном языке (например, *«какие эксперименты проводились со сплавом железо-никель»*). Система ищет по графу и векторному индексу, возвращает карточку сущности и список всех связанных сущностей (эксперименты, процессы) из смежных статей, а также summary, авторов и ссылки на скачивание оригиналов.
3. **Фильтрация.** Пользователь ограничивает поиск по типу процесса, материалу, географии, году.
4. **Работа с историей.** Чаты сохраняются, можно возвращаться к предыдущим обсуждениям.
5. **Визуализация связей.** Отображаются интерактивные цепочки «материал → процесс → оборудование → результат», связанные эксперты и лаборатории.
6. **Расширение онтологии (Админ-сценарий).** Если система обнаруживает сущности, не подходящие под текущие типы, администратор/учёный получает уведомление, добавляет новый тип в онтологию, и документ переобрабатывается.

### 1.4. Ключевые принципы

1. **Данные только реальные (No Hallucinations).** LLM не выдумывает документы, авторов или факты. Все метаданные и ссылки подставляет backend из БД.
2. **Граф — инструмент, а не самоцель.** Граф используется для фильтрации, построения цепочек и поиска связей. Простой семантический поиск осуществляется через векторный индекс.
3. **Строгая и эволюционирующая онтология.** Извлекаются только сущности из закрытого списка. Никакого «мусора в графе». Если LLM находит сущность вне онтологии, она не выдумывает новый тип, а помечает её для ручного расширения онтологии человеком.
4. **Разделение слоёв (Decoupling).** Хранение файлов, метаданных, графа и векторов — независимые сервисы с чёткими контрактами.
5. **Переносимость LLM.** Бизнес-логика абстрагирована от провайдера LLM. Код не зависит от того, используется ли внешний API или локальный inference.

## Часть 2. Стек технологий

| Слой | Технология | Назначение |
| :--- | :--- | :--- |
| **Язык** | Python | Backend, ML-пайплайны |
| **Frontend** | React 18 + TypeScript | Интерфейс пользователя |
| **Визуализация графа** | react-cytoscapejs | Интерактивные графы, подсветка противоречий |
| **Backend** | FastAPI | REST API, оркестрация |
| **Фоновые задачи** | Celery + Redis | Асинхронная обработка документов, прогресс-бары |
| **Парсер PDF** | Docling (IBM) | PDF → Markdown + картинки с метаданными |
| **Конвертация** | LibreOffice headless | Fallback для DOCX/PPTX → PDF (если требуется) |
| **Граф знаний** | Neo4j | Хранение сущностей и связей, обход графа |
| **Метаданные и чаты** | PostgreSQL 15 + pgvector | История чатов, метаданные документов, векторный поиск |
| **Хранилище файлов** | PostgreSQL `bytea` (MVP) → MinIO | Исходные PDF/DOCX/PPTX |
| **LLM (текст)** | Yandex GPT 5 | Анализ текста, извлечение сущностей, генерация ответов |
| **LLM (vision)** | Yandex GPT 5 Vision | Анализ графиков, таблиц, схем |
| **Embedding** | multilingual-e5-large | Векторное представление чанков |
| **Оркестрация** | docker-compose | Локальная разработка и деплой |

> *Примечание: Версии библиотек не фиксируются в документе — определяются на этапе сборки, чтобы не блокировать обновления безопасности.*

## Часть 3. Онтология

### 3.1. Сущности (узлы графа)

| Сущность | Описание | Примеры |
| :--- | :--- | :--- |
| **Material** | материал | никель, сульфат никеля, гарниерит, сплав Fe-Ni |
| **Process** | процесс | кучное выщелачивание, биоокисление, автоклавная плавка |
| **Equipment** | оборудование | реактор, колонна, автоклав, флотационная машина |
| **Property** | свойство | концентрация, pH, температура, прочность на разрыв |
| **Experiment** | эксперимент | серия опытов, описанная в статье |
| **Publication** | публикация | статья, доклад, отчёт |
| **Document** | загруженный документ | PDF/DOCX/PPTX с метаданными |
| **Expert** | эксперт | автор, исследователь |
| **Facility** | лаборатория или институт | ИМет УрО РАН, ЦНИИчермет |
| **Condition** | условие | холодный климат, кислая среда, режим 80°C |
| **Country** | страна | Россия, Китай, Австралия (для фильтра «своё/зарубежное») |
| **Claim** | утверждение | (этап 2, для реификации противоречий) |

### 3.2. Связи (рёбра графа)

| Связь | Семантика |
| :--- | :--- |
| **uses_material** | процесс или эксперимент использует материал |
| **operates_at_condition** | процесс или оборудование работает при условии |
| **produces_output** | процесс или эксперимент производит результат |
| **described_in** | сущность описана в документе |
| **validated_by** | результат подтверждён экспертом или публикацией |
| **contradicts** | противоречие (этап 2, через Claim) |

### 3.3. Правила извлечения

1. **Закрытый список.** Тип сущности строго из предопределенного списка (п. 3.1). Никаких кастомных типов на лету.
2. **Лимиты.** Не более 5 сущностей каждого типа и 10 связей на один документ.
3. **Дедупликация.** Обязательное приведение к `canonical_label` + использование `aliases` (Fe / Iron / Железо → `Fe`).
4. **Отсечка шума.** Запрет на извлечение общих понятий («исследование», «метод», «результат»).
5. **Порог значимости.** Сущность попадает в граф только если она встречается ≥ N раз, связана обязательной связью или упомянута в заголовке/аннотации/выводах.
6. **Формат.** Строгий валидный JSON, проверяемый через Pydantic.
7. **Эволюция онтологии (Ontology Evolution).** Если Extraction-LLM обнаруживает сущность, которая не подходит ни под один текущий тип, она **не создаёт новый тип**. Вместо этого она возвращает структурированное предупреждение (массив `unclassified_entities` с текстом сущности и контекстом). Это триггерит задачу для администратора рассмотреть сущность и добавить новый тип в онтологию. После обновления онтологии документ переобрабатывается.

## Часть 4. Целевой Pipeline загрузки документа

Пользователь загружает PDF через React-интерфейс
↓
Backend принимает файл, создаёт job, возвращает job_id.
Оригинальный PDF параллельно сохраняется в filestore.
↓
Docling парсит PDF → document.md + images/ + manifest.json
(сохранение структуры: заголовки, таблицы, формулы, подписи к картинкам)
↓
Фильтрация изображений (отсеиваем декоративные)
↓
Текст + картинки отправляются в Yandex GPT (multimodal-запрос):
• Модель анализирует текст статьи
• Для каждой картинки: тип (график/таблица/схема), ключевая информация
• Результат: enriched_document.md (текст + описания картинок)
↓
Извлечение сущностей и связей (Extraction-LLM)
↓
Канонизация + валидация (Pydantic)
• Если найдены unclassified_entities → сохраняются в PostgreSQL
как «предложения к онтологии», документ помечается как
«требует расширения онтологии»
↓
Запись в БД (если валидация успешна):
• Исходный PDF → filestore (Postgres bytea / MinIO)
• Метаданные → PostgreSQL
• Сущности и связи → Neo4j (Cypher-запросы MERGE)
• Чанки + embedding → pgvector
↓
Прогресс через Redis → React опрашивает GET /jobs/{job_id}/status
и отображает пошаговый статус
