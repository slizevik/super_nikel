# Что за проект?

Проект Nikelpower является сервисом для ученых-материаловедов, целью которого является возможность искать данные из общей базы данных исследований, докладов, статей и презентаций, общаясь с LLM через чат. Также, ученые могут добавлять свои документы в базу данных.

Сервис состоит из 2 вкладок - "Загрузка документов" и "Чат с LLM".

Далее описаны основные требования для реализации данного проекта.

# Минимальные требования

- Язык программирования - Python 3.11.9;
- База данных - Neo4j в связке с Graphiti Zep;
- Backend - fastapi;
- Frontend - streamlit;
- LLM - уточняются на этапе описания требования к приложению;
- Используй Docker для создания контейнера со всеми зависимостями. Docker файл используй тот, который лежит в папке с проектом. Если библиотеки установлены - не скачивай заново, проверь сначала, что всё скачано.
# База данных

Требования к БД:
1. Основная графовая БД - Neo4j. К данной БД необходимо сделать интеграцию с Graphiti Zep для дальнейшей работы с LLM;
2. Embedding - на твоё усмотрение;
3. LLM должна быть достаточно простой, чтобы быть способной обработать данные из БД и на основе запроса найти релевантный ответ;
4. LLM должна быть способна сгенерировать структурированный ответ;
5. Модель не должна выдумывать несуществующие документы, а обращаться только к РЕАЛЬНЫМ данным из БД.

В БД должны быть обязательно следующие сущности (при необходимости можешь другие сущности):
Material, Process, Equipment, Property, Experiment, Publication, Expert, Facility.

Между сущностями должны быть обязательно следующие связи:
uses_material, operates_at_condition, produces_output, described_in, validated_by, contradicts.

Должно быть обязательно: хранение графа с поддержкой сложных запросов на обход связей (Cypher, Gremlin или аналог)
# Backend

## Алгоритм работы вкладки "Загрузка документа"

1. Пользователь отправляет документ и информацию по категории документа через Frontend;
2. Если полученный документ имеет расширение НЕ PDF, то:
	- Загруженный документ переводится в pdf формат с помощью libreoffice. Скачай libreoffice с docker hub, пропиши в dockerfile backend все необходимые зависимости. необходимо встроить в архитектуру приложения без конфликтов. проверь согласованность всех используемых библиотек;
3. Над документом в формате PDF производится подготовка к загрузке в базу данных:
	1. В документе отдельно извлекаются весь текст документа и все изображения. Текст переносится в отдельный файл, который в следующих шагах будет загружен в БД. Назовем этот файл "подготовленный документ". Дальнейшие шаги производятся только с изображениями:
		1. Каждое изображение в документе заменяется на специальный технический текст, который обозначает уникальный ID изображения;
		2. Все изображения, последовательно, должны передаваться в LLM Qwen3-VL через API. Составь промпт, в котором пропиши, чтобы модель обязательно вернула в ответе следующее:
			- указание типа картинки (график, таблица или любая другая категория);
			- если это график или таблица, то проведи подробный анализ и оставь только ключевую информацию о графике, полезную с точки зрения материаловедения;
			- для всех остальных категорий модель должна определить, поможет ли это для анализа документа, если да, то описывает изображение, если нет, то пишет что изображение бесполезно.
		3. Полученное описание, по ID, вносятся в "подготовленный документ", заменяя технический текст на описание, соответствующее ID
4. Из "подготовленного документу" извлекаются основные сущности по промпту (сам промпт введу я введу позже);
5. Извлеченные сущности загружаются в базу данных, используя выбранный тобой embedding + в БД заносится информация о категории документа. Также сам документ в исходном виде должен быть загружен в БД;
6. Каждый выполняющийся шаг обработки документа должен отображаться в Frontend части (пример: Выполняю: "Конвертацию в PDF");
7. Верни на Frontend сообщение об успешности загрузки документа. Если на каком-либо этапе выполнения приложения возникла ошибка - она также возвращается пользователю.

## Алгоритм работы вкладки "Чат с LLM"

1. Пользователь направляет запрос, в котором описано необходимая ему информация, которую он хочет получить из БД;
2. В соответствии с фильтром на поиск материалов по стране, установленным в Frontend, запрос должен автоматически дополнятся 
3. Запрос отправляется на AI-агента;
4. AI-агент направляет запрос в БД с целью поиска наиболее схожей информации в соответствии с запросом. Используй для этого метрику косинусной близости векторов;
5. Найденную информацию из БД AI-агент должен представить в максимально подробном варианте в виде списка документов, возвращая в ответе следующее:
	1. Название документа;
	2. Краткое summary по документу, соответствующее информации по запросу пользователя;
	3. Автора документа или источник;
	4. Даты актуализации;
	5. Ссылка на скачивание документа в исходном виде.
6. Дополнительные требования к итоговому ответу:
	- Многоуровневой фильтрации: по типу процесса, материалу, географии, году публикации, уровню достоверности
	- Числовых диапазонов и условий: «найти решения для концентрации сульфатов <200 мг/л»
	- Сравнительных запросов: «отечественная практика» vs «мировая практика», «вариант А» vs «вариант Б»
7. 8. Если данные отсутствуют и не найдено ни одного источника - указать на отсутствие данных;
8. Сформированный ответ возвращается на Frontend.

# Frontend

## Общие требования

1. Используй streamlit для создания GUI;
2. Создай 2 отдельные вкладки, соответствующие приложениям "Чат с LLM" (вкладка по умолчанию) и "Загрузка документов";
3. Переключение между вкладками должно осуществляться через боковое меню;
4. Минималистичный дизайн
## Вкладка "Чат с LLM"

1. Сделай поле с пользовательским вводом текста и кнопку отправки запроса;
2. Добавь возможность выставить фильтр из 2 вариантов ответов с возможностью выбора обоих: отечественные источники, зарубежные источники;
3. Сделай кнопку создания нового чата с LLM;
4. Создай историю чатов, хранящуюся на стороне сервера (пока что только одного пользователя). Записывай данные по истории чатов и всех сообщений внутри чатов в БД PostgreSQL 15 (пропиши PostgreSQL в dockerfile);
5. В боковой панели должна быть возможность переключения между чатами;
6. Также должна быть реализована визуализация графа по следующим пунктам:
	- Отображение цепочек: «материал → процесс → оборудование → результат»;
	- Подсветка противоречивых данных или пробелов: «нет экспериментов для комбинации: холодный климат + кучное выщелачивание + никелевая руда»;
	- Показ связанных экспертов и лабораторий по теме запроса;

## Вкладка "Загрузка документов"

1. Поле с загрузкой файла;
2. Выпадающее окно с выбором следующих категорий:
	- доклады;
	- журналы;
	- материалы конференций;
	- обзоры;
	- статьи;
	- другое - при выборе данной категории должно высвечиваться поле пользовательского ввода текста, в котором пользователем обязательно  прописывается названии категории (минимум 3 символа).
3. Кнопка "Загрузить в базу данных", при нажатии на которую отправляется запрос на Backend в приложение "Загрузка документов";
4. После нажатии кнопки необходимо вывести круговой progress bar, текстом показывающий текущий выполняющийся шаг на Backend части;
5. Вывели сообщение об успешности загрузки документа. Если на каком-либо этапе выполнения приложения возникла ошибка - она также возвращается пользователю.
