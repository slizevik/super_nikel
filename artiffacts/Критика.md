Краткое саммари диалога
С чего начали. Пользователь попросил список Python-библиотек, альтернативных Streamlit, с современным интерфейсом. Я предложил Gradio, Marimo, NiceGUI, Flet, Reflex, Panel, Dash и другие.

Переход к проекту Nikelpower. Пользователь предоставил md-файл с описанием сервиса для учёных-материаловедов: загрузка документов, чат с LLM, граф знаний на Neo4j + Graphiti Zep, backend на FastAPI, frontend на Streamlit. Я выступил в роли критика и выявил ключевые проблемы:

конфликт между Graphiti и ручным извлечением сущностей;

хранение бинарных файлов в Neo4j;

неопределённость с LLM (простая vs сложные задачи);

отсутствие нужных сущностей (Condition, Country, Claim);

нечёткие связи и правила извлечения;

риски галлюцинаций LLM при формировании метаданных и ссылок;

ограничения Streamlit для сложного UI и прогресс-баров.

Корректировка требований. Пользователь принял замечания и попросил решения по пунктам 1 и 2. Я предложил:

строгую нормализацию и системный промпт для извлечения сущностей;

три варианта хранения файлов (MinIO, Postgres bytea, файловая система) с рекомендацией Postgres для MVP;

отдельный сервис filestore;

упрощение до сценария S2: ограниченная онтология + векторный поиск;

абстракцию LLMProvider для переключения между внешним API и локальной моделью;

добавление сущностей Condition, Country, Document, Chunk;

флаг «своё/зарубежное» как поле origin.

Обновлённый md и переход на React. Пользователь попросил переписать md: заменить Streamlit на React, не фиксировать версии библиотек, разделить идею и реализацию, подробно описать техническую идею. Я подготовил полный обновлённый документ с двумя частями (Идея и Техническая реализация), описал онтологию, пайплайны загрузки и чата, контракты API, оркестрацию через docker-compose. В конце добавил Mermaid-диаграмму end-to-end процесса: загрузка статьи → извлечение сущностей → запись в БД → поиск через чат → ответ со ссылками.

Гипотеза об экономии токенов. Пользователь спросил, можно ли парсить PDF скриптами, чтобы экономить токены, и какие есть альтернативы Qwen3-VL. Я подтвердил гипотезу: скриптовый парсинг сокращает расход токенов в 5–20 раз. Предложил:

для таблиц: Camelot, pdfplumber, tabula-py;

для формул: pix2tex, pdf-formula;

для векторных графиков: pdf-diagram-extract;

для текста: PyMuPDF, Marker, MinerU.
VLM вызывать только для растровых графиков, сложных таблиц и семантического анализа изображений. В качестве замены Qwen3-VL рекомендовал лёгкие специализированные модели: PaddleOCR-VL (0.9B), Qianfan-OCR (4B), Gliese-OCR-7B, DharmaOCR Lite (3B), NuExtract3 (4B).

К чему пришли. Итоговая архитектура Nikelpower:

Frontend на React + TypeScript;

Backend на FastAPI + Celery + Redis;

Граф знаний на Neo4j + Graphiti;

Метаданные, чаты, файлы — PostgreSQL + pgvector, отдельный сервис filestore;

LLM через абстракцию LLMProvider (внешний API для прототипа, локальный vLLM/Ollama в институте);

Пайплайн загрузки: скриптовый парсинг PDF (текст, таблицы, формулы, векторные графики) → VLM только для сложных случаев → извлечение сущностей по системному промпту → запись в Neo4j и pgvector;

Гибридный поиск: векторный + Cypher-фильтры;

Ответ формируется backend’ом: метаданные и ссылки подставляются из БД, LLM пишет только summary;

Рекомендуемая VLM для основного потока — PaddleOCR-VL, fallback — Qianfan-OCR или Gliese-OCR-7B.
