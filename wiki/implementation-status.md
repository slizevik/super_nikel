# Текущее состояние и план реализации SuperNikel

Документ сверяет фактическую реализацию с целевым видением из
[FINAL.md](./FINAL.md). Это рабочий план для персонального помощника по
магистерской диссертации о машинном обучении и локализации мРНК, а не
утверждение, что все целевые функции уже готовы.

**Срез реализации: 04.11.2026.** Статус описывает код в рабочем дереве
репозитория на эту дату. Изменения сохранения чатов присутствуют в рабочем
дереве, но пока не зафиксированы Git-коммитом.

## Краткий вывод

Уже реализован основной сквозной сценарий MVP: приложение сканирует папку с
PDF, индексирует извлечённый текст, ищет по нему и формирует ответ с цитатами
на найденные статьи. Есть русский интерфейс запросов и сохранение отдельных
чатов.

До целевого продукта не хватает прежде всего не графовой базы или новых
персон, а доказанной на личной библиотеке надёжности поиска и ответов,
постраничной прослеживаемости, режима перевода и функций для текста
диссертации. Перед расширением следует проверить полный сценарий в
контейнерах и собрать фиксированный набор вопросов для оценки качества.

## Что уже реализовано

### Библиотека и индексация

- Backend сканирует `LIBRARY_ROOT` рекурсивно и принимает в основную
  библиотеку PDF. Исходные файлы остаются в папке пользователя, подключённой
  к backend и worker только для чтения.
- Для файлов сохраняются относительный путь, размер и SHA-256. Повторное
  сканирование отличает неизменённые, изменённые и новые файлы; ошибки и
  состояния обработки показываются в интерфейсе.
- Celery worker извлекает текст PDF с помощью существующего парсера
  PyMuPDF/Docling, сохраняет индексируемый текст и манифест. Для файлов
  библиотеки этот путь не вызывает LLM.
- PostgreSQL хранит метаданные документов, задания и извлечённый текст;
  полнотекстовый поиск использует PostgreSQL. Redis используется как брокер
  фоновых задач.
- Интерфейс показывает список документов, статус обработки и путь к исходному
  файлу; можно запустить повторное сканирование.

### Поиск и ответы

- Есть API вопроса по библиотеке и интерфейс чата с ответом на русском языке.
- Для запроса с кириллицей backend получает английский перевод через
  настроенную облачную модель. Дополнительно используется ограниченное
  детерминированное расширение терминов для поиска датасетов.
- Сейчас полнотекстовый поиск выполняется по извлечённому тексту документа,
  а не по активному поиску среди семантических векторов.
- Модель получает найденные текстовые фрагменты, а не всю библиотеку.
  Backend проверяет, что ID цитируемых документов входят в результаты
  поиска, и формирует цитаты с именем файла, путём и фрагментом.
- При отсутствии результатов модель не вызывается; API возвращает сообщение,
  что соответствующие фрагменты не найдены.

### Чаты

- В рабочем дереве реализованы отдельные чаты, список и восстановление
  сообщений через API и интерфейс.
- Миграция `0008_persistent_chat_history` добавляет таблицы чатов и сообщений;
  сохраняются вопросы, ответы, переводы запроса и цитаты. Заголовок первой
  беседы предлагается моделью, при ошибке используется резервный заголовок.
- PostgreSQL использует Docker volume, а backend применяет Alembic-миграции
  перед запуском. Это должно сохранять историю при пересоздании контейнеров,
  но фактическое применение миграции и сквозное сохранение в Docker ещё
  требуют проверки.
- История отображается, но предыдущие сообщения не передаются модели для
  разрешения контекста последующих вопросов.

## Что реализовано частично или пока не подтверждено

- **Надёжность на реальной коллекции не доказана.** Есть тесты компонентов,
  но не завершён стабильный сквозной прогон сканирования личной папки и
  проверки ответов на фиксированных вопросах.
- **Поиск работает на уровне документов.** Активный answer retrieval
  использует полнотекстовый индекс извлечённого текста и расширение запроса;
  интерфейса поиска фрагментов без генерации ответа пока нет.
- **Цитата привязана к документу и фрагменту, но не к странице.** Текущий
  контракт цитаты не содержит номера страницы и отдельного перехода к месту
  в PDF.
- **Метаданные статьи извлекаются ограниченно.** При сканировании имя файла,
  путь и хэш доступны, но автоматическое надёжное заполнение названия,
  авторов, года и DOI ещё не подтверждено.
- **Есть заготовки для чанков и векторов, но они не являются рабочим
  поисковым путём.** В схеме модели чанка задан вектор размерности 1024 и
  `intfloat/multilingual-e5-large`, тогда как настройки приложения содержат
  `embedding_dimensions=256` и модель Yandex embeddings. Перед включением
  embeddings нужно выбрать одну модель и согласовать размерность, схему,
  миграции и вычисление векторов.
- **Качество ответа проверяется не полностью.** Проверяется принадлежность
  ID цитаты найденным документам, но система не доказывает автоматически,
  что каждое утверждение ответа следует из соответствующего фрагмента.
  Различение «датасет упомянут» и «датасет использовался в эксперименте»
  требует отдельной проверки на примерах.
- **Чаты ещё не прошли проверку на работающем PostgreSQL в контейнерах.**
  Также не реализована передача истории чата в контекст модели.

## Целевые функции, которых пока нет

- Перевод выбранной статьи или её раздела по запросу, с сохранением
  структуры, ссылок, формул и научных терминов.
- Загрузка и анализ текста диссертации, поиск утверждений без источников и
  предложения дальнейших разделов с опорой на уже написанное и библиотеку.
- Локальная модель или явный пользовательский контроль над передачей
  фрагментов облачному провайдеру. Сейчас конфигурация поддерживает Yandex
  Cloud и GigaChat; само расположение PDF на локальном диске не означает, что
  отправляемые модели фрагменты остаются локальными.
- Персоны и специализированные внешние справочные базы. Это поздние
  необязательные расширения, а не условие успешного MVP.

Старый upload/extraction pipeline и Neo4j-инфраструктура остаются в
репозитории, но не являются ядром сценария локальной библиотеки. Их не следует
расширять в рамках движения к целевому продукту без отдельного обоснования.

## План действий

Последовательность сохраняет этапы из [FINAL.md](./FINAL.md), но сначала
закрывает разрыв между написанным кодом и проверенной работой приложения.

### Этап 0. Зафиксировать воспроизводимое текущее состояние

1. Зафиксировать незакоммиченные изменения чатов отдельным коммитом после
   проверки состава изменений.
2. Запустить PostgreSQL, Redis, backend, worker и frontend в одном актуальном
   Compose-окружении; применить миграции без удаления Docker volumes.
3. Пройти сценарий: сканирование папки → готовый статус → вопрос → ответ с
   цитатами → новый чат → перезапуск backend/контейнеров → восстановление
   обоих чатов и сообщений.
4. Отдельно записать ошибки этого прогона и базовое время ручного поиска по
   одной и той же выборке статей.

**Готово, когда:** сквозной сценарий проходит после перезапуска, история и
цитаты сохраняются, а запуск и проверка воспроизводимы по инструкции.

### Этап 1. Довести библиотеку и извлечение текста

1. Прогнать сканирование на реальной личной папке и проверить пропуски,
   дубликаты, изменённые PDF, повреждённые файлы и поведение при недоступном
   источнике.
2. Проверить порядок текста на двухколоночных статьях, обработку переносов и
   качество результата извлечения.
3. Решить, какие метаданные нужны для личного сценария; в первую очередь
   показывать имя статьи и доступные год/авторов/DOI, не подменяя
   отсутствующие сведения догадками.
4. Зафиксировать поведение удалённых из папки документов и возможность
   повторной индексации после ошибки.
5. Сохранять индексацию без вызова LLM.

**Готово, когда:** повторный скан не создаёт дубликатов, изменённые статьи
переиндексируются, а состояние каждого документа объяснимо пользователю.

### Этап 2. Сделать поиск измеримым и улучшать его по результатам

1. Подготовить 30–50 вопросов по своей тематике и отметить ожидаемые статьи
   и подтверждающие места: модели, методы, датасеты, сравнения, неоднозначные
   термины и вопросы без ответа в библиотеке.
2. Добавить простой поиск/просмотр найденных фрагментов без обязательного
   вызова LLM, чтобы можно было отдельно оценить retrieval.
3. Измерить, находит ли текущий полнотекстовый поиск ожидаемые статьи и
   фрагменты. Отдельно проверить русские вопросы и английские формулировки.
4. Сначала исправить конкретные пробелы в нормализации терминов и словаре
   области. Перевод вопроса уже существует; оценивать нужно его влияние на
   найденные результаты.
5. Подключать семантический поиск только если зафиксированные ошибки
   полнотекстового поиска им обосновывают это. Перед этим согласовать модель
   embeddings, размерность векторов, chunking и индексы. Сравнить hybrid
   retrieval с текущим поиском на том же наборе запросов.

**Готово, когда:** для каждого тестового запроса можно увидеть найденные
источники и оценить полноту поиска, а усложнение ранжирования улучшает
измеримый результат, а не только архитектуру.

### Этап 3. Повысить проверяемость ответов и цитат

1. Привязать извлечённые фрагменты к страницам PDF и добавить страницу в
   контракт цитаты, если парсер предоставляет надёжную нумерацию.
2. Проверять ответы на фиксированном наборе вопросов: релевантность,
   подтверждение утверждений, полноту источников, точность цитаты и
   корректный отказ при нехватке данных.
3. Включить примеры, где статья только упоминает датасет и где она явно
   сообщает его использование; добиться, чтобы ответ не смешивал эти случаи.
4. Сохранять консервативный ответ или отказ, когда фрагменты недостаточны;
   не считать наличие ссылки само по себе доказательством корректности
   ответа.
5. Решить на основании тестов, нужен ли контекст предыдущих сообщений чата.
   Если нужен, передавать только ограниченную историю и применять те же
   ограничения на источники для каждого ответа.

**Готово, когда:** пользователь может открыть нужную статью и быстро сверить
цитату; ошибки и случаи отказа фиксируются на тестовом наборе.

### Этап 4. Определить приватный режим до работы с текстом диссертации

1. Явно обозначить в интерфейсе, что отправляется облачному провайдеру при
   переводе запроса и генерации ответа.
2. Выбрать режим для личных и неопубликованных материалов: осознанное
   подтверждение облачной обработки или локальный inference.
3. Не добавлять анализ полного текста диссертации, пока выбранный режим
   обработки данных не понятен и не проверен.

**Готово, когда:** пользователь до отправки текста понимает, какие данные
передаются и как работает выбранный режим.

### Этап 5. Добавить перевод статей по запросу

1. Дать возможность выбрать индексированную статью или её фрагмент.
2. Переводить по частям с сохранением структуры, ссылок, формул,
   идентификаторов и терминов.
3. Показывать рядом источник, исходный текст и статус машинного перевода;
   явно обрабатывать неполный или плохо распознанный текст.
4. Проверить результат на небольшом наборе статей и терминов направления.

**Готово, когда:** выбранный раздел можно перевести и сверить с оригиналом,
не переводя всю библиотеку заранее.

### Этап 6. Добавить анализ текста диссертации и поддержку планирования

1. Начать с явной загрузки или выбора файла с текстом, не с фонового
   наблюдения за редактором.
2. Показывать структуру и темы текущего текста, возможные утверждения без
   источников и совпадающие статьи из личной библиотеки.
3. Для каждого предложения указывать, на какой фрагмент диссертации и какие
   источники оно опирается.
4. Формулировать дальнейшие разделы и вопросы как варианты для автора, не
   генерировать окончательные научные выводы или текст без подтверждения.

**Готово, когда:** рекомендации можно проверить по тексту пользователя и
источникам библиотеки, а решение остаётся за автором.

### Этап 7. Рассматривать персоны и дополнительные базы как опцию

После устойчивой работы основных этапов можно добавить роли общения или
специализированные справочные базы. Внешние сведения нужно явно отделять от
сведений личной библиотеки; персоны не должны ослаблять проверку источников.

**Готово, когда:** для каждой дополнительной роли есть конкретный полезный
сценарий, который нельзя закрыть проще основным интерфейсом.

## Как измерять результат

Главная метрика соответствует [FINAL.md](./FINAL.md): время от вопроса до
найденного и проверенного фрагмента. Для одинакового набора вопросов нужно
сравнить ручной поиск по папке и поиск через приложение. Дополнительно
фиксировать:

- долю вопросов, для которых найдена ожидаемая статья и фрагмент;
- точность цитат и долю утверждений, подтверждённых источниками;
- случаи ложного совпадения и корректного отказа;
- ошибки индексации и повторной обработки файлов;
- время ответа и время проверки источника пользователем.

Не заявлять процент «точности ИИ», пока нет проверенного и повторяемого
набора вопросов с эталонными источниками.

## Что не следует делать ради этой цели

- Возвращать граф знаний и извлечение сущностей в центр MVP без измеримой
  пользовательской задачи.
- Включать embeddings только потому, что `pgvector` или таблица чанков уже
  присутствуют в схеме.
- Переводить все статьи заранее или отправлять всю библиотеку модели.
- Начинать с автономного написания диссертации, постоянного наблюдения за
  документами или настройки множества персон.
- Удалять PostgreSQL volume при проверках сохранения чатов.
